# Public matchmaking

Every supported game exposes Play now through shared routes. PostgreSQL is the only required database for matchmaking and temporary chat. Redis remains optional on a single persistent realtime server and supports shared Socket.IO broadcasts and presence.

## Assignment

`game:queue_join` validates the definition's `configSchema` and accepts turn-based and simultaneous engines with `reduce`. The group size is `engine.playerCount?.(config) ?? 2` and must be an integer within the engine's player bounds. A definition may list find-page variants in `queues` (for example 1v1 and 2v2); each variant sends its own config and is therefore its own pool. `games.joinMatchmaking` takes a PostgreSQL transaction advisory lock, checks for an existing active public game, and renews one ticket per account. Queue joins are limited to 30 per minute per socket. Tickets expire after 45 seconds; the client refreshes every 10 seconds and on reconnect. Compatible renewals preserve queue age. A new tab replaces ticket ownership, so cleanup from an older tab cannot cancel it.

The oldest `groupSize - 1` unexpired tickets with the same game type and canonical JSONB config are selected; with fewer, the caller keeps waiting. Self-matches are excluded. Seat order is shuffled with `crypto.randomInt`, avoiding an advantage tied to queue order. Seat `i` gets `roleForSeat(i)`; when the config's `mode` is `"teams"`, seats alternate teams `A` and `B` by index, otherwise each seat is its own team. Public queues never add bots. This is an unranked random-opponent pool with FIFO waiting fairness, not rating-based matching.

Every seat, the initial state (created by the server with a fresh seed), and the active game are inserted in the same transaction that removes the matched tickets. Failure rolls everything back. Duplicate concurrent joins recover the same active game. The acknowledgement returns the assigned code; `match_found` also reaches every matched user's room, and the server arms the turn or round clock immediately. A lost event is recovered by another join. Cancellation uses the same lock and returns an assigned game if matching already won the race.

The global assignment lock favors a small, clear correctness boundary. It serializes queue mutations across server processes. High-volume queues should partition the lock and preserve the one-active-game invariant before scaling further. Leases limit stale queued players but cannot promise a peer remains online after assignment.

## Identity and authorization

Public games have no permanent conversation and both seats are assigned before clients enter. HTTP snapshots, room joins, chat reads, and chat sends require participant membership. Outsiders receive no match details. Players, moves, `winner`, `winners`, and the viewer ID use `<room-code>:<role>` aliases. Names are Player 1 through Player N; avatars and creator/challenge identities are hidden. Engines with hidden information additionally redact state and moves through `publicState` / `publicMove` for every viewer. Public matches are excluded from profile game history and series endpoints. Registered engines must store roles and rules only, never profile data.

## Chat and friendship

Temporary text uses `match:message` and a dedicated `match_message` table. It is available in every active game without a conversation: public matches and private standalone rooms, for any number of participants. Messages are delivered to each human participant's user room rather than the game room, so spectators of a private room never receive them. Public authors are aliases; private rooms use real user IDs and keep profile popups. Bodies are trimmed, limited to 1,000 characters, and validated by strict shared schemas. A client UUID deduplicates retries. Sending is limited to one message per second per participant and 500 messages per match. Reads return the latest 100 visible messages. Only active games can send or read chat.

The UI closes chat when the game ends. Records remain privately stored for safety for seven days from sending, then an hourly startup-and-runtime cleanup deletes expired rows. Expired messages are filtered from reads even before cleanup. Account IDs remain available only to authorized backend operations; this is anonymous between players, not anonymous to the service operator. Database backups need their own retention policy.

Friend consent applies to public matches only. A player chooses a specific participant with `match:friend { gameId, playerId }`, where `playerId` is that participant's alias; `match_friend_choice` stores one row per (game, chooser, target). Nothing is revealed until two players have chosen each other, and every pair in an N-player match is independent. Choices can be made during the match or within 15 minutes after it ends. Mutual consent creates an accepted friendship, applies guest friend limits, opens a fresh permanent DM, sends `match:friends { gameId, playerId, peerUsername }` to both users, and updates both social sidebars. The ack is `{ ok, mutual, playerId, peerUsername }`. `GET /api/matches/:code/messages` returns `messages`, `choices` (aliases the viewer chose), and `friends` (`{ playerId, username }` for mutual pairs). Temporary messages are never copied. Private rooms use the existing profile friend requests instead.

## Execution and recovery

All supported games use the shared runner (`game-runner.ts`). A process-local per-game lock serializes transitions, and each persist locks the active row and compares the expected state before committing state, ordered move history, outcome, winners, and stats; a miss from another process reloads and retries. Repeated or racing reductions cannot overwrite a newer turn, and simultaneous locks from different players all persist. Timeout aborts use the same expected-state guard.

Turn clocks allow 30 seconds initially and 30 seconds minus five seconds per consecutive timeout later, with a ten-second floor. A real move clears strikes. The third consecutive timeout aborts; every attentive player wins by forfeit. Simultaneous engines use a round clock of `roundTimeMs(state)`; on expiry every pending player receives the engine's `autoMove` and a strike, and the engine decides what long-absent players forfeit. Public assignment starts the clock even before browser room joins. Reconnect resumes persisted state and move history.

Run one persistent realtime instance. Timers and strikes are process-local, and a process restart grants a fresh deadline when an active game is recovered by queue join or room join. PostgreSQL transactions make assignment and move persistence safe across processes, but they do not provide durable timer ownership. Horizontally scaling gameplay requires durable deadlines and a single clock owner per game.

## Verification

`matchmaking-flow.test.ts` exercises concurrent duplicate joins, queue ownership, config pools, leases, and cancellation. `simultaneous-platform.test.ts` assembles 2v2 matches from concurrent joins with alternating teams. `public-chat.test.ts` exercises identity redaction, participant checks, send retries, rate limits, completion visibility, expiry deletion, mutual consent, stale timeouts, and exactly-once stats. `match-chat-rooms.test.ts` covers N-player aliases and pairwise consent, private-room chat with real identities, and conversation games staying on permanent chat. The local synthetic smoke script plays both private and public tic-tac-toe over authenticated WebSockets, reconnects, chats, befriends, and sends a permanent message, then plays Tank Arena in a private team lobby and in public 1v1 and 2v2 queues. No external database URL is needed for those tests.
