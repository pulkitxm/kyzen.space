# Testing

The runner is **`bun:test`** (no Jest/Vitest). Every workspace keeps its tests in a `tests/` directory; `apps/server` additionally has an `integration/` suite (25 files) - twenty-three are DB-backed and need a live database, and two (`presence-redis.test.ts`, `health-probe-redis.test.ts`) are Redis-backed and need a reachable Redis. Tests are mostly fast, dependency-free unit tests over pure helpers, plus a set of **structural** suites that enforce the platform contract - every registered game must ship an engine, schemas, a board, a skeleton, and a doc, or a test fails.

## How to run

```bash
bun run test                # turbo run test - every workspace's `test` script
```

Per-workspace (cd in, or `--filter`):

```bash
cd packages/games-core && bun test            # one package's suite
cd packages/shared && bun test tests/theme.test.ts # one file
bun test --filter "<pattern>"                  # filter by test name
```

The server's default `test` script runs only `tests/` (`apps/server/package.json` → `"test": "bun test tests"`). The DB-backed suite is separate:

```bash
cd apps/server && bun run test:integration     # runs integration/ with --env-file=../../.env
```

Variables already set in the environment take precedence over `.env`, so the suite can target any disposable database: migrate it with `DATABASE_URL=... bun run db:migrate` from the repository root, then run `DATABASE_URL=... REDIS_URL=... BETTER_AUTH_SECRET=... bun run test:integration`.

Integration tests **self-skip without a DB**: each file probes `select 1` and gates with `describe.skipIf(!DB_UP)`, so they pass cleanly when Postgres is down - but to actually exercise them, start the DB (`bun run db:start`) and provide `.env`. The two original files keep the probe inline (`apps/server/integration/game-flows.test.ts:14`, `apps/server/integration/chat-flows.test.ts:18`); the nineteen newer DB-backed files import a shared `DB_UP` from `apps/server/integration/harness.ts:8`. One of those, `apps/server/integration/_preflight.test.ts`, is the **opt-out** of the skip: it *throws* when `DB_UP` is false (with a setup checklist) instead of skipping, so a misconfigured environment fails loudly rather than passing on a silently-empty suite.

`harness.ts` factors out the boilerplate: `createHarness(prefix)` returns `makeUser`/`befriend`/`makeDm`/`makeGroup`/`trackGame`/`cleanup` over UUID-namespaced fixtures (so parallel files never collide), plus `unwrap`/`expectErr`/`TestUser`. Each edge/driver file does `const h = createHarness("…")` and `afterAll(h.cleanup)`, which deletes its tracked games/conversations/users. The two original files still carry their own copy of this harness inline. Some of the newer edge files go below the repository layer and insert rows **directly** via the `db`/`schema` barrel exports - `pagination-tiebreak-edge.test.ts` and `chat-gates-edge.test.ts` use an explicit `createdAt` or a direct `db.update` role promotion to set up states the public API won't produce, then assert through the repositories/services.

The two Redis-backed integration files exercise real Redis rather than a DB, so they need a reachable `REDIS_URL`: `presence-redis.test.ts` covers `RedisPresenceStore`, and `health-probe-redis.test.ts` covers the `/health` probe round-trip (`runHealthProbe`). The `redis` service in `compose.dev.yaml` (`redis:7` on `localhost:6379`) is a standard service brought up alongside Postgres by `bun run db:start` (and `bun run db:reset`). In CI it's the `redis` service on the `integration` job.

## Patterns to know

**`renderToStaticMarkup` without a DOM.** Web component tests import `renderToStaticMarkup` from `react-dom/server` and assert on the returned HTML string - no jsdom, no DOM globals. `apps/web/tests/game-skeletons.test.tsx:20` renders `<DefaultGameSkeleton />` and asserts `expect(html).toContain("animate-pulse")`; the tic-tac-toe skeleton test resolves the board via `getGameSkeleton(TIC_TAC_TOE)` and counts `size-24` cells to confirm a 9-cell board; `PlaySkeleton` is rendered for each `ChatLayout` variant and probed for layout markers (`border-l`, `360px`, `shadow-2xl`, `rounded-r-lg`). The avatar tests do the same with the real DiceBear engine, asserting the output starts with `<svg`. The same no-DOM pattern now covers the `games-client` React primitives directly (`playing-card`/`skeletons`/`marks.test.tsx`): `PlayingCard`/`Joker`/`CardBack` assert the `role="img"` svg and the per-instance id prefixes, `SkeletonBox`/`DefaultGameSkeleton` assert the `animate-pulse` markup, and `TttMark` asserts the X/O color class and the decorative-vs-labeled aria branch.

**`mock.module` for server plumbing.** Server route/handler tests stub the data layer instead of touching Postgres. The DB layer is now the `@kyzen/database` package, so the mock targets it: `mock.module("@kyzen/database", () => ({ games, profiles, … }))` (`apps/server/tests/turn-based.test.ts:68`) then `await import("../src/realtime/turn-based")` (`:83`). The `requireAuth` test follows the same shape, mocking `../src/auth` before importing the middleware; the route tests (`gifs-route.test.ts`, `notifications-route.test.ts`) mock the provider/auth (and, for notifications, the **complete** `@kyzen/database` barrel) before importing the router, then drive it with `router.request(...)`. Because Bun's `mock.module` can leak across files, the barrel mock is always **complete** (every export present); the `@kyzen/database` index re-exports its value bindings as owned consts so a barrel mock does **not** write through to the source modules. Pure helpers are exported so they're unit-testable independent of HTTP/socket plumbing. See `docs/architecture/server-api.md` for the routes → services → repositories layering this leans on.

**A fake simultaneous engine and in-memory games.** `apps/server/tests/support/fake-rounds.ts` defines a small synthetic simultaneous engine (rounds, sealed locks, teams, bots, a `LEAVE` value that takes a seat out, a `resultDelayMs` replay delay, redaction, queues) and `support/memory-games.ts` an in-memory games repository with compare-and-swap semantics, a per-batch `persists` log, and a `beforePersist` hook for simulating another process. It yields with `setImmediate`, which fake timers leave alone. `support/runtime.ts` re-installs the `@kyzen/games-core` registry mock (real games plus the fake) and a complete `@kyzen/database` mock in each file that uses them, because module mocks leak between files. The integration suite reuses the fake engine through `installFakeRegistry()` and inserts its lobby rows directly.

**Injected dependencies and real database concurrency.** Presence handlers accept fake dependencies, and Redis presence unit tests use an in-test `FakeRedis`. Public matchmaking and temporary chat use real PostgreSQL integration tests because transaction locks, leases, JSONB equality, and concurrent retries are the behavior under test.

**A preload that seeds env for unit tests.** The server's unit suite runs with a preload - `apps/server/bunfig.toml` sets `[test] preload = ["./tests/setup.ts"]` - and `apps/server/tests/setup.ts` defaults the required env vars (`DATABASE_URL`, `BETTER_AUTH_SECRET`, `LOG_LEVEL`) with `||=` if they're unset. That lets the real `env`/`db`/`logger` modules import without throwing during unit tests, even with no `.env` present.

**Structural contract suites.** Several suites iterate `GAMES`/`listGameTypes()` rather than hard-coding a game, so adding a `GameDefinition` automatically extends coverage - and forgetting any required artifact fails CI:

- no board / no skeleton → `packages/games-client/tests/registry.test.ts`
- no `docs/games/<type>.md` → `packages/games-core/tests/game-docs.test.ts`
- invalid schema / category / roles / cover image → `conformance.test.ts`

This is the testing half of the "adding a game needs no new routes, endpoints, or tables" contract.

## CI

`.github/workflows/ci.yml` runs the same Make targets used locally on every pull request and push to `main`, with no path filters. It separates lint, formatting, types, unit tests, policy/scheduler tests, dead code, audit, workflow lint, secret scanning, and build results. Runtime jobs run the Postgres/Redis integration suite and production/development smoke flows in disposable synthetic environments. The aggregate `CI required` check fails when any mandatory job fails or is cancelled or skipped.

Run `make ci` for all checks, or `make ci-test`, `make ci-integration`, and `make ci-smoke` separately. Heavy local targets wait for available CPU and memory across concurrent worktrees; GitHub bypasses the scheduler. Full commands, tool requirements, resource settings, and isolation rules are in [docs/ci.md](../ci.md).

## Tracked-file policies

`bun run check` uses Biome CI mode with warnings treated as failures. `bun run lint` checks lint and imports; `bun run format:check` checks formatting. Focused tests, statically skipped tests, debugger statements, explicit `any`, unused declarations, and non-null assertions are errors. Source code cannot use console logging except warnings and errors; command-line entry points write their results to stdout.

`bun run check:comments` checks all tracked code and configuration, including SQL migrations, SVG and Markdown markup comments, TOML, shell/Python scripts, environment examples, and workflow scripts. It preserves functional directives and migration statement breakpoints. Markdown headings and documentation prose remain valid. `bun run strip-comments` removes disallowed comments; its `--check` mode never rewrites files. The generated pattern SVGs retain their Lucide ISC attribution in metadata.

`bun run check:em-dashes` checks tracked text and symlink target names for U+2014. `bun run check:repository` rejects local hook tooling, automatic lifecycle scripts, stray tracked environment files, and merge markers. These checks inspect Git's tracked paths with NUL delimiters and never follow symlinks into local data. `bun run test:policies` exercises the commands in disposable Git repositories, including failure cases and read-only checks.

There are no local Git hooks. Run these commands explicitly when useful; CI enforces them on pull requests and `main`.
