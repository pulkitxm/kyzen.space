# playing-cards: themed card rendering

## What this is / why it matters

Playing cards are drawn **from code as inline SVG**, not loaded from static image files. The art (52 faces + 2 jokers + a back) is generated by a pure builder, and a thin React component injects that markup into the page so it lives in the page's CSS scope. That last part is the whole point: an inline SVG can read the app's theme variables, so the cards **recolor with the active theme**. A `<img src="card.svg">` or a CSS `background-image` cannot — those load in an isolated document that can't see `var(--…)` or `currentColor`.

Like the rest of the codebase, the card code follows the **logic ↔ UI split**:

- **`@gamelobby/games-core`** holds the *logic*: a framework-agnostic SVG **builder** that returns markup strings (`packages/games-core/src/playing-cards/svg.ts`). No React.
- **`@gamelobby/games-client`** holds the *UI*: `"use client"` components that render the builder's markup inline (`packages/games-client/src/playing-cards/playing-card.tsx`).
- **`@gamelobby/shared`** owns the *types + constants*: `Suit` / `Rank` / `JokerVariant` and the `CARD_SUITS` / `CARD_RANKS` lists.

There are **no card image assets** and **no generator script** to run — rendering a card is a function call. (This replaced an earlier `scripts/generate-deck.js` that wrote `public/games/playing-cards/*.svg`.)

## The public API

### React components — the normal way to render

Import from `@gamelobby/games-client`:

```tsx
import { PlayingCard, Joker, CardBack } from "@gamelobby/games-client";

<PlayingCard suit="hearts" rank="Q" className="h-auto w-full" />;
<Joker variant="red" className="h-auto w-full" />;
<CardBack className="h-auto w-full" />;
```

- `PlayingCard` props: `suit: Suit`, `rank: Rank`, plus optional `className` / `style`.
- `Joker` props: optional `variant?: JokerVariant` (default `"red"`), plus `className` / `style`.
- `CardBack` props: just `className` / `style`.

All three render an `<svg viewBox="0 0 360 504">` and inject the art with `dangerouslySetInnerHTML` (`playing-card.tsx:41`, `:60`, `:75`). They are `"use client"` components and already namespace their SVG ids per instance — see [Multiple cards on one page](#multiple-cards-on-one-page-id-prefixing-gotcha-2) below.

### String builders — for non-React / tests / standalone files

Import from `@gamelobby/games-core`. Two flavors per card:

| Function | Returns |
| --- | --- |
| `cardSvg(suit, rank, idPrefix?)` (`svg.ts:427`) | A complete `<svg>…</svg>` document string (with `xmlns`, `viewBox`, `role`, `aria-label`). |
| `cardInner(suit, rank, idPrefix?)` (`svg.ts:418`) | Just the inner markup (`defs` + body), no `<svg>` wrapper — this is what the React component injects. |
| `jokerSvg(variant, idPrefix?)` / `jokerInner(…)` (`svg.ts:440`/`:431`) | Same split for a joker. |
| `cardBackSvg(idPrefix?)` / `cardBackInner(…)` (`svg.ts:449`/`:444`) | Same split for the card back. |
| `cardLabel(suit, rank)` (`svg.ts:423`), `jokerLabel(variant)` (`svg.ts:436`) | The `aria-label` strings (e.g. `"Q of Hearts"`). |
| `CARD_VIEWBOX` / `CARD_WIDTH` / `CARD_HEIGHT` (`svg.ts:5`/`:3`/`:4`) | `"0 0 360 504"`, `360`, `504`. |

Use `*Svg` when you want a freestanding file/string (e.g. writing a `.svg`, an email, a test snapshot). Use `*Inner` when you control the `<svg>` element yourself (as the React component does). **Note:** a standalone `cardSvg(...)` string rendered *outside* the app DOM falls back to the baked hex colors — theming only happens when the markup is inlined into a page that defines the theme variables (see [Theming](#theming)).

## Recipes: generating each kind of card

A face / number / ace card (rank is any `Rank` — `"A"`, `"2"`…`"10"`, `"J"`, `"Q"`, `"K"`):

```tsx
<PlayingCard suit="spades" rank="K" className="h-auto w-full" />;
```

The card back:

```tsx
<CardBack className="h-auto w-full" />;
```

A joker (red or black):

```tsx
<Joker variant="black" className="h-auto w-full" />;
```

The whole deck:

```tsx
{CARD_SUITS.map((suit) => (
  <div className="grid grid-cols-13 gap-2" key={suit}>
    {CARD_RANKS.map((rank) => (
      <PlayingCard className="h-auto w-full" key={`${suit}-${rank}`} rank={rank} suit={suit} />
    ))}
  </div>
))}
```

### Generating the back specifically

The back is produced by `backMarkup()` (`svg.ts:389`) and exposed exactly like the faces: render `<CardBack />` in React, or call `cardBackSvg()` / `cardBackInner(idPrefix)` for a string. `cardBackInner` composes `defs()` + `frame()` + `backMarkup()` and then prefixes ids (`svg.ts:444`). The back itself is three layers, all themed:

1. A felt field — a rounded rect filled `url(#backField)` (the `--pc-back` / `--primary-dark` gradient).
2. A diagonal lattice — `url(#backPat)`, a gold (`--pc-gold`) diamond pattern.
3. A center medallion — concentric gold rings around the four suit pips and a hub.

To restyle the back, edit `backMarkup()` (geometry/markup) and/or the `backField` / `backPat` gradients in `defs()` (colors). It needs no separate entry point — `<CardBack>` picks up whatever `backMarkup()` returns.

## Why it must render inline (gotcha #1)

The components inject markup with `dangerouslySetInnerHTML` into a real `<svg>` element so the SVG becomes part of the page DOM and inherits the page's CSS — that is what lets `var(--accent-warm)` etc. resolve. **Do not** reintroduce `<img src=".../card.svg">`, `next/image`, or `background-image` for these cards: those isolate the SVG and theming silently stops working (you'd get the fallback hex on every theme). The `dangerouslySetInnerHTML` call carries a `biome-ignore lint/security/noDangerouslySetInnerHtml` directive (`playing-card.tsx:40`) because the markup is generated by our own builder, never user input.

## Theming

Themeable paints are written as a **nested-fallback CSS variable**: `var(--pc-X, var(--theme-token, #hex))` (defined once at `svg.ts:17`–`:19`). Resolution order:

1. `--pc-X` if set (a per-card override hook; not defined anywhere by default).
2. else the app theme token (`--accent-warm` / `--primary` / `--primary-dark`), defined per theme in `apps/web/app/globals.css` (`html[data-theme="…"]` + `html.dark` / `html:not(.dark)`).
3. else the baked `#hex` fallback (so standalone/un-themed markup still looks right).

| Card element | Variable | Theme token | Fallback hex |
| --- | --- | --- | --- |
| Gold foil border, rule lines, crowns/jewelry, panel border, back lattice & rings | `--pc-gold` (`svg.ts:17`) | `--accent-warm` | `#c79a3e` |
| Court-figure robes (and the joker tunic) | `--pc-robe` (`svg.ts:18`) | `--primary` | `#c8102e` |
| Card-back felt field | `--pc-back` (`svg.ts:19`) | `--primary-dark` | `#6e1226` |

What deliberately **does not** theme:

- **Suit pips + rank indices** stay classic: hearts/diamonds `#C8102E` (red), spades/clubs `#16161D` (black). These come from `SUITS[suit].color` (`svg.ts:10`).
- **The card face** stays cream (`url(#card)`), so red/black pips are always legible regardless of theme.
- Figure details (skin, hair, steel) keep their painted colors.

The metallic sheen is preserved while theming via `mix()` (`svg.ts:21`), which emits `color-mix(in srgb, <base> <pct>%, <white|black>)` to derive the highlight/shadow stops of each gradient from the themed base color. `color-mix` is supported in current evergreen browsers.

To **override** card colors independently of app chrome, define the `--pc-*` variables on any ancestor (e.g. a wrapper `style={{ "--pc-gold": "#d4af37" }}`); the cards under it use your value instead of the theme token.

## Sizing & layout

The `<svg>` has a `viewBox` but **no `width`/`height`**, so it has no intrinsic size — the consumer sizes it. The common pattern is `className="h-auto w-full"` inside a width-constrained container (a grid/flex cell); the SVG then scales to the cell's width and derives its height from the 360×504 aspect ratio (`preserveAspectRatio` defaults to `xMidYMid meet`). The coordinate system is `360 × 504` with the center at `(180, 252)`.

## Multiple cards on one page: id prefixing (gotcha #2)

SVG element ids (`goldFoil`, `robe`, `cardClip`, …) are **document-global**, and `url(#id)` references resolve to the *first* matching id in the document. With several inline cards that would make every card reuse the first card's gradients/clips. The builder prevents this: `prefixIds()` (`svg.ts:407`) rewrites every `id="…"` and `url(#…)` with a per-instance prefix. The React components derive a stable prefix from React's `useId()` (`playing-card.tsx:15`, inside `useIdPrefix()` at `:14`), which is consistent across SSR and hydration — so there is no hydration mismatch and no need to pass anything.

If you call the **builder** directly and render more than one inline on a page, pass a unique `idPrefix` yourself (e.g. `cardInner("hearts", "Q", "a-")`, `cardInner("spades", "K", "b-")`).

## Transparent border & no baked shadow

The card body is opaque cream, but everything **outside** the rounded card boundary is transparent, and **no drop-shadow is baked into the SVG**. Apply elevation/shadow in CSS on the wrapper (e.g. `drop-shadow` / `box-shadow`) so it can match motion and stacking. `frame()` (`svg.ts:93`) draws only the face + gold border.

## Anatomy of the SVG (for editing the art)

Card markup is assembled as `defs()` + `frame()` + (per card) body, then id-prefixed. Key pieces in `svg.ts`:

| Function | Draws |
| --- | --- |
| `defs()` (`:61`) | All gradients/filters/patterns/clips: `card`, `vignette`, `goldFoil`, `gold`, `robe`/`robeDark`, `backField`, `backPat`, `diaper`, `emboss`, `gild`, `grain`, `cardClip`, `topClip`. |
| `frame()` (`:93`) | Cream face + the gold border rules (no shadow). |
| `panel(suit)` (`:104`) | The central rounded "window" behind court figures. |
| `indices(rank, suit)` (via `indexContent`) | The two diagonal corner labels (rank glyph + small pip). |
| `numberPips(rank, suit)` (`:196`) + `LAYOUTS` (`:122`) / `COL` (`:121`) | The pip grid for `2`–`10`; `LAYOUTS` maps each rank to `[column, y]` pairs, `COL` is the L/C/R x-positions. |
| `aceContent(suit)` | The single large center pip + flourish for the Ace. |
| `queenFigure` / `kingFigure` / `jackFigure` (+ shared `FACE`, `faceFeatures`, `ROBE`, `bodicePanel`) | The court portraits; each is clipped to `topClip` and mirrored to fill the panel (`courtCard`, `:327`), which `cardContent` (`:343`) dispatches to by rank. |
| `backMarkup()` (`:389`) | The card back (felt + lattice + medallion). |
| `jesterMarkup(variant)` (`:350`) | The joker (hat lobes, face, motley, marotte, "JOKER" lettering). |
| `pip(suit, cx, cy, scale, rot?, color?, flat?)` (`:40`) | The reusable suit symbol — places a heart/diamond/spade/club path, scaled/rotated, optionally embossed. |

## Adding or customizing card art

- **Recolor an existing element to follow the theme:** reference it as `var(--pc-x, var(--theme-token, #hex))` in `defs()` (reuse `--pc-gold`/`--pc-robe`/`--pc-back`, or add a new `--pc-*` base near `svg.ts:17`). Keep a hex fallback.
- **Change the back / a court figure / the joker:** edit the corresponding function (`backMarkup`, `*Figure`, `jesterMarkup`). The components need no changes.
- **Add a new card variant or surface:** add a builder function in `svg.ts`, export it from `packages/games-core/src/index.ts`, and (if it needs DOM) add a `"use client"` wrapper in `playing-card.tsx` exported from `packages/games-client/src/index.ts`.
- **Keep suit pips red/black** unless you intend to theme them — readability on the cream face depends on it.
- The repo is **comment-free** (`CLAUDE.md`) and Biome-checked: write self-documenting code, and remember the `useId()`-based prefix when adding any component that renders inline.

## Tests

`packages/games-core/tests/playing-cards.test.ts` asserts: every `CARD_SUITS` × `CARD_RANKS` combination renders a labeled `<svg>`; jokers and the back render; themeable parts reference `var(--pc-…)`; suit pips keep `#C8102E` / `#16161D`; no `url(#shadow)` is baked in; and `idPrefix` namespaces both `id="…"` and `url(#…)` so instances don't collide. Run it with `cd packages/games-core && bun test tests/playing-cards.test.ts`.
